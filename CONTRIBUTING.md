# Contributing to `@haraka/email-address`

Thanks for taking the time to look at this code. This document captures
the conventions this repo follows so a PR can land cleanly without a
back-and-forth on style or layout.

## Repository layout

```
index.js                Public API: thin wrappers + re-exports.
index.d.ts              TypeScript declarations (hand-maintained).
lib/                    ESM source, one module per concern.
  cursor.js             Shared regex constants + Cursor + parseError.
  literals.js           [...] address-literal parsing (IPv4 / IPv6 / IDN).
  envelope.js           RFC-5321 envelope grammar.
  header.js             RFC-5322 header grammar.
  address.js            Address + Group classes (+ private format helpers).
  validator.js          parseAddress / isValid (plain-email validator).
  name-utils.js         Personal-name heuristics (nameCase, extractName, ...).
dist/                   Auto-generated, mirrors source tree under each format dir.
  cjs/
    index.cjs           CJS mirror of index.js.
    lib/*.cjs           CJS mirrors of every lib/*.js.
scripts/
  build-cjs.js          Regenerates every .cjs from its matching .js.
.githooks/
  pre-commit            Re-runs build-cjs.js when any .js is staged.
test/
  envelope-*.js         RFC-5321 envelope-grammar tests.
  header-*.js,
  header-corpus.txt     RFC-5322 header-grammar tests + ported corpus.
  validator.js          parseAddress / isValid tests.
  name-utils.js         Personal-name helper tests.
  cjs.cjs               CJS-loader smoke test (runs the whole API
                        through `require()`).
examples/
  esm.mjs, cjs.cjs      Runnable demos, byte-identical output.
```

`lib/` modules form a dependency graph:

```
cursor   ← (leaf)
literals ← cursor
envelope ← cursor, literals
address  ← cursor, literals, envelope, name-utils
header   ← cursor, literals, address
index    ← address, header, validator, name-utils
```

## Dual-package layout

ESM is the source of truth. Every `*.js` file under the root and `lib/`
has a matching `*.cjs` generated by `scripts/build-cjs.js`, written to
the parallel `dist/cjs/` tree. **Never edit the `.cjs` files by
hand** — the auto-generated header at the top tells you they're
regenerated.

- `npm run build:cjs` — regenerate every mirror on demand.
- `npm run check:cjs` — exits non-zero if any mirror is stale (CI uses this).
- `.githooks/pre-commit` runs the build whenever you stage any `*.js`
  and `git add`s the regenerated `*.cjs` automatically. The hook is
  wired up the first time you run `npm install` in this repo (via the
  `prepare` lifecycle script).
- `prepack` re-runs the build so the published tarball is always coherent.

If you add a new file in `lib/`, add it to `SOURCES` in
[`scripts/build-cjs.js`](scripts/build-cjs.js) and to the `files`
list in `package.json`.

### What the generator expects

Every ESM source file must:

1. Optionally start with a `^// `-prefixed comment block (stripped from
   the CJS output, replaced with the auto-gen warning).
2. Use single-line `import { … } from '…'` statements — multi-line
   import lists aren't supported by the rewriter.
3. End with a single `export { … }` block, optionally followed by an
   `export default { … }`. The generator collapses both into
   `module.exports = { … }` + `module.exports.default = module.exports`.

Don't use `export function foo()` / `export const foo` — collect every
public name in the trailing block instead. (`lib/name-utils.js` shows
the pattern.)

## Coding conventions

- **ES2024+ idioms**: `for…of`, optional chaining, nullish coalescing,
  `??=`, top-level `await` where it fits. No legacy patterns (`var`,
  `function() {}` callbacks, `Promise.then` chains for sync code).
- **`node:`-prefixed imports** for built-ins: `import { domainToASCII } from 'node:url'`, not `'url'`.
- **No new runtime dependencies.** The package is zero-dep and plans to stay that way;
- **No new files unless the task requires it.** Prefer extending an
  existing `lib/` module to creating another.
- **Comments explain _why_, not _what_.** Function names already
  explain what. Use comments to flag a non-obvious RFC reference, an
  ABNF production, a workaround for a particular real-world mailer,
  or a deliberate divergence from the spec.
- **No commented-out code in commits.** If it's not used, delete it.

## Parsers — extending the grammar

- New character classes belong in `lib/cursor.js` alongside the others.
  Use the sticky `y` flag plus the Unicode `u` flag where non-ASCII
  matters; never use backreferences or nested quantifiers (ReDoS
  surface).
- Productions follow recursive descent against the `Cursor` interface
  in `lib/cursor.js`. Every production either advances the cursor and
  returns a parsed value, or throws via `parseError`. No silent
  rewinds — if you need lookahead, save the position explicitly.
- Reuse the existing primitives (`ATEXT_RE`, `parseDotString`,
  `parseAddressLiteral`, `parseHeaderQuotedString`, etc.) before
  writing a new one. Most new productions are small wrappers around
  the existing building blocks.
- Add a new option to the public entry points only if there's a clear
  use case. Default behaviour stays RFC-strict.
- Relaxations of the strict RFC grammar — particularly RFC-5322 §4.4
  obs-\* productions — go behind `postel: true`, not on by default. When
  adding a new postel-mode relaxation, document it in `index.d.ts`
  (the `EnvelopeParseOptions` / `HeaderParseOptions` JSDoc) and in the
  README options table. Never relax control-character handling
  (obs-NO-WS-CTL, obs-qp with control chars) — those would open
  header-injection surface and are out of scope even with `postel`.

## Tests

- One file per concern, named after the part of the public API it
  exercises. `envelope-*.js`, `header-*.js`, `validator.js`, etc.
- Use `node --test` (the built-in runner) and `import assert from 'node:assert/strict'`.
- Group related cases under `describe(…)` blocks; each `it(…)` should test one observable behaviour.
- Bug fixes start with a failing test, then the fix that turns it green.
- Cross-module-system smoke lives in `test/cjs.cjs` — when you add a
  new top-level export, add an assertion there that `require()`
  exposes it too.
- New features need a corresponding test file. High coverage is the norm — every `lib/` module has direct or behavioural coverage.

## Commands at a glance

```sh
npm test              # full suite (ESM + CJS)
npm run build:cjs     # regenerate every .cjs mirror
npm run check:cjs     # CI gate — stale mirrors fail
npm run lint          # eslint (flat config, @haraka/eslint-config)
npm run prettier      # prettier check (auto-gen .cjs files are ignored)
npm run format        # prettier:fix + lint:fix
npm run versions      # npm-dep-mgr drift check
```

Before opening a PR: `npm test && npm run lint && npm run prettier &&
npm run check:cjs`. If you're touching `index.js` or any `lib/*.js`,
the pre-commit hook will keep your CJS mirrors in sync for you.

## Git

- Conventional Commits for messages: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`.
- Keep commits focused. Refactors, behaviour changes, and doc updates should be separate commits.
- PR titles match the leading commit; PR body explains the _why_ and links to any relevant RFC sections.

## Standards reference

- RFC 5321 — SMTP envelope addresses (§4.1.2 paths, §4.1.3 literals, §4.5.3.1 length limits).
- RFC 5322 — Message-header addresses (§3.4 syntax, §4.4 obsolete forms).
- RFC 6531 / 6532 — SMTPUTF8 / EAI (Unicode local-parts + domains).
- RFC 5890 / 5891 / 5892 + UTS #46 — IDNA2008 (handled through Node's `url.domainToASCII`).
- RFC 1035 §2.3.4 — 63-octet sub-domain label cap.

The conformance table in [README.md](README.md#standards-conformance) records how each RFC is handled.
